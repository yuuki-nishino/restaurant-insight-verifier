# ADR-0003: Jevの実際のプリミティブ（Choice/Score/Noul）への設計マッピング

日付: 2026-09-24
ステータス: 承認（メニュー分類部分は[ADR-0004](./0004-action-guidance-replaces-menu.md)、感情部分は[ADR-0005](./0005-sentiment-mixed-and-more-aspects.md)で廃止・置き換え）

## コンテキスト

`docs/api-spec.md`の初期版は、Jevの実APIを確認する前に書いた想定スキーマ（`aspect`配列+confidence、自由記述の`menu_mentioned`、`is_supported`のtrue/false）だった。実際にTypeSafe（Jev提供元）のライブドキュメント（https://docs.typesafe.ai/）を読んだところ、JevのAPIは以下3種類の「質問プリミティブ」しか持たないことが分かった。

| プリミティブ | 答える内容 | 返り値 |
| --- | --- | --- |
| Choice | 定義済みの選択肢から1つ | `choice`, `probabilities`, `confidence` |
| Score | 順序尺度上の位置 | `score`, `legend`, `probabilities`, `confidence` |
| Noul | Yes/Noの確率 | `noul`（0〜1の確率のみ、confidenceなし） |

自由記述の抽出（想定していた`menu_mentioned`）はサポートされていない。また複数該当しうる分類（アスペクト）は、公式ドキュメントで「Noulを項目ごとに1つずつ使う」ことが明示的に推奨されている。

## 決定

口コミ分類を以下のようにJevの実プリミティブにマッピングする。

1. **アスペクト判定**: 「味」「接客」「待ち時間」「清潔さ」「コスパ」の5項目それぞれについて、独立したNoul質問（例:「この口コミは『味』について言及しているか」）を1リクエストにまとめて送る。複数該当は複数のNoulがそれぞれ高い値を返すことで自然に表現される。「その他」という明示的なバケツは作らず、どのアスペクトのNoulも低い場合を「特定のアスペクトに言及していない」として扱う。
2. **感情判定**: `sentiment`はChoice（`positive` / `negative` / `neutral`の3択）。
3. **メニュー言及**: 自由記述抽出ができないため、事前に定義した固定のメニュー名リスト（例: 醤油ラーメン、味噌ラーメン、塩ラーメン、とんこつラーメン、つけ麺、餃子、チャーシュー丼など）＋「メニューの言及なし」を選択肢に持つChoiceに変更する。メニューリストはサンプルデータ作成時に確定させ、後から調整可能な設定値として扱う。
4. **インサイト検証**: `is_supported`はChoiceのtrue/falseではなくNoul（「この主張は集計データと整合するか」への確率）に変更する。true/falseの二値はNoulの方が自然に表現でき、確信度の判断（0.5付近＝要確認）もそのまま使える。

## 理由

- Jevの実際のAPI仕様に合わせないと実装できないため、想定スキーマをそのまま使うことはできない。
- 複数該当ラベルの分類はNoulの推奨パターンそのものであり、公式ドキュメントの用法に従うのが最も素直。
- メニューは自由記述よりも固定リストのChoiceの方が、店主が実際に見るダッシュボード集計（メニュー別言及ランキング）とも相性が良い（表記揺れが起きない）。

## 影響

- `docs/api-spec.md`のJev API仕様セクションを、実際のリクエスト/レスポンス例に書き換える。
- `docs/data-model.md`の`ReviewClassification`型を、アスペクトごとのNoul値・Choiceの感情・Choiceのメニューに合わせて更新する。
- メニューリストはコード内の設定値（例: `src/lib/menu.ts`）として持ち、サンプルデータやダッシュボードの実装と合わせて随時調整する。
- アスペクトの項目自体（現在5項目）も、運用しながら増減しやすいように配列/設定として持たせる。
