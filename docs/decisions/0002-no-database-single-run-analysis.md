# ADR-0002: DBを持たず、投入から表示までを1リクエストで完結させる

日付: 2026-09-24
ステータス: 承認

## コンテキスト

初期構想（[plan.md](../plan.md)）ではSupabaseに口コミ・分類結果・インサイト・検証結果を永続化する設計だったが、MVPの目的は「Jevを使った口コミ分析アプリを作ること」自体であり、データの永続化や複数店舗・複数期間の管理はスコープ外である。DBのセットアップ・スキーマ設計・保存処理はMVPの検証したい価値（Jevによる分類と事実検証の有用性）に対して不要なオーバーヘッドになっていた。

## 決定

Supabase（DB）を廃止し、口コミ投入からダッシュボード・インサイト表示までを1回のリクエスト（1セッション）内でメモリ上のみで処理する。ページをリロードすると結果は失われ、再度口コミを投入して分析をやり直す前提とする。

これに伴い、Jevの検証クエリも「先月比」のような期間をまたぐ比較は行わず、**今回投入したデータの集計結果の中で完結する主張**（例：「待ち時間への不満が全体の35%を占め、最も多い」）のみを検証対象とする。

## 理由

- 1日で動くデモを作り切るというMVPの制約下では、DB設計・接続・保存処理よりも、Jevによる分類→集計→LLMによる要約→Jevによる事実検証、というコア体験を早く動かすことを優先すべき。
- 永続化を前提にすると「先月比」のような時系列比較の検証が必要になり、複数期間分のデータ投入・管理という別のスコープが発生してしまう。DBを外すことで、この複雑さも同時に取り除ける。
- リロードで結果が消えることは、単発デモとしては許容できる制約である。

## 影響

- `docs/architecture.md` のデータフロー図からSupabaseのノードを削除し、集計処理をサーバー側のメモリ処理として明記する。
- `docs/data-model.md` はDBスキーマではなく、処理ステージ間でやり取りするデータの型定義（リクエスト/レスポンスの形）を記述する内容に変更する。
- `docs/api-spec.md` の検証クエリの入力例・出力例を、期間比較なしの形に更新する。Claude側のプロンプト方針にも「時系列比較はさせない」旨を明記する。
- GitHub Issuesのうち、Supabase作成（#2）と分類結果のDB保存（#6）はクローズし、口コミ投入画面（#4）・ダッシュボード（#7）の内容を更新する。
- 将来、複数回の分析結果を比較したくなった場合は、このADRを置き換える新しいADRを作り、DBまたは他の永続化手段の追加を検討する。
